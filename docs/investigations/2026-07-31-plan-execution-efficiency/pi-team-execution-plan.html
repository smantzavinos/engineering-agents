Proposal · Pi only · Team mode only

Pi Team Execution

Talk until the intent is clear, freeze it into one plan.md contract, put the tasks on a board, let a small team execute with review-on-handoff, read the summary at the end. Every arrow below is labeled with who pulls the trigger: the human, an agent's tool call, or an extension firing automatically.

01Trigger taxonomy

Four kinds of trigger exist in the whole system. Everything in the diagrams and tables below is tagged with one of these.

HUMAN

You act manually. Chat messages, slash commands (/pi-team-plan), approvals, DMs from the /messenger overlay. The only inputs the process requires from you: intent, risk approvals (rare), reading the summary.

AGENT TOOL

An agent decides to call a tool. Lead writes plan.md, calls task.create, spawns workers via subagent, commits. Workers reserve/release and edit files. Deliberate, visible in transcripts.

EXTENSION AUTO

Fires without anyone asking. Crew auto-review on every task completion, reservation blocking on conflicting edits, stuck-agent detection, completion notifications. LSP diagnostics and checkpoint refs apply to the lead session.

BOARD EVENT

File-state change wakes an agent. Task becomes ready (dep met) → idle worker claims. Handoff → reviewer wakes. NEEDS_WORK → fresh worker retries with findings. Board empty → lead closes. Messages arrive as steering prompts. Nothing polls on a timer.

02Roles & responsibilities

Five roles. Three are agents, one is a mechanism, one is you. Escalation is a rule, not a role: one retry carrying the findings, then the lead rescues with a strong subagent, then it asks you.

Human

you · HUMAN

  • Set intent in normal conversation
  • Approve only when asked, or on risk flags
  • Watch live via /messenger overlay (optional)
  • Read the closing summary; iterate if needed
  • Babysit execution

Lead

primary Pi session · AGENT TOOL

  • Converse → write plan → run 4 plan gates
  • Materialize board, dispatch workers
  • Broad gate once per wave, then commit (only committer)
  • Escalations, close, telemetry, summary
  • Implement tasks; read full diffs

Worker ×1–4

fresh subagent per task · model = task lane · AGENT TOOL

  • Claim ready, file-disjoint task; reserve write set
  • Implement + run its cheap inner-loop check
  • Handoff ≤15 lines: files, check output, assumptions, risks
  • Same contract at every tier — lane picks the model, not the role
  • Commit; run broad suites; claim outside write set

Reviewer

fresh Crew reviewer per handoff · EXTENSION AUTO

  • Verdict on every handoff: SHIP / NEEDS_WORK / RETHINK
  • NEEDS_WORK → fresh worker retries, findings + progress log injected
  • Verdict parsed to SHIP / NEEDS_WORK / MAJOR_RETHINK
  • Fix code; approve its own findings

Board

pi-messenger crew — files, not an agent · BOARD EVENT

  • Task DAG, statuses, dependencies, waves
  • File reservations that block with a named holder
  • Wakes agents on events; live overlay for the human

02bModel tiers — lanes route models, not roles

Three intelligence tiers across the whole process. The plan tags every task with a lane; the lane picks the worker's model. A task qualifies for cheap only if it is decision-complete — executable from its packet row plus referenced contracts/decisions with zero judgment calls. Target ≥ 50% of tasks on cheap (measured: $0.60 vs $3.10 per task, no quality loss); a plan that can't hit that hasn't settled enough decisions — a planning signal, not a routing problem.

A lane is a Team role — that is the entire routing mechanism. task.create accepts no model, but it accepts role, and a Team role carries model, thinking and skills (crew/team/types.ts:13-17). work resolves task.model → wave param → roleModel → config.models.worker → session model (crew/handlers/work.ts:176-183), so one role string sets all three. Lanes are declared once in the Team profile, and materialization stays on the public API — no direct store writes.

Two traps. Never name a lane with a bare packaged role (worker, scout, reviewer…): resolution prefers the packaged canonical name when that key also exists, and packaged non-editing roles cannot edit. The worker-* prefix is safe. And the profile must be active — otherwise every lane silently falls back to the default worker model with no error.

03Skills & entry points

Three human-triggered skills carry disable-model-invocation: true — Pi cannot discover or auto-load them, so they cost zero context until you type the slash command. Only the two execution skills are model-discoverable.

SkillTriggerModel-discoverable?What it does
/discovery HUMAN No — disable-model-invocation Optional. Socratic pushback mode for genuinely fuzzy problems. Most work never needs it — plain conversation covers discovery.
/design HUMAN No — disable-model-invocation Optional. Structured option-comparison with throwaway scout/researcher fanout. Output lands in chat, not artifacts.
/pi-team-plan HUMAN No — disable-model-invocation The pivot. Creates plans/<date>-<slug>/ and freezes the conversation into plan.md (Intent · Contracts · Decisions · Checks · Tasks), runs the 4 mechanical gates, requests approval only if risk-flagged or requested, else starts execution.
pi-team-lead AGENT TOOL Yes The lead's execution protocol: board materialization, dispatch, wave gates, escalation rules, close sequence. Loaded when execution starts.
pi-team-worker BOARD EVENT Injected into worker packets Worker contract: claim/reserve/implement/check/handoff/release. Stated once here, never restated in plans.
Why disable-model-invocation? Skills Pi can discover sit in every system prompt. Discovery/design/plan are deliberate human decisions — hiding them from the model keeps ~3 skill descriptions out of every turn's context and prevents Pi from ceremonially "entering discovery mode" when you just wanted a conversation.
One contract, one directory. The plan lives at plans/<date>-<slug>/plan.md. The directory may also hold notes/ (reference material, research, superseded drafts) and, generated at close, review.md and telemetry.md. Only plan.md is injected into task packets — everything else is human reference and never enters an agent's context unless a task row explicitly cites it. If a worker needs a note to do its job, the plan didn't freeze enough: fix the plan, don't add a reference.

06Remediation & escalation — sequence

What happens when review fails. The core rule: retry once with findings, then escalate to the lead. Retry #1 reuses the worker's own context (re-discovery was ~27% of measured runtime); a failed retry means the context holds the wrong mental model, so escalation is always fresh.

08Context rules

Context is the scarce resource. Workers get a packet, not a transcript; the lead never ingests full diffs (they flow worker → reviewer directly); handoffs are ≤15 lines.

fresh + packet

Worker, first attempt

A packet (write set · contract · decisions · check) beats inheriting a transcript.

fresh + findings

Worker, retry #1

Not a choice: Crew workers run --no-session. Crew re-injects task spec, review feedback, and ~30 progress lines.

fresh + strong

After failed retry

The old context holds the wrong model — that's why it failed.

fresh, always

Every reviewer

Independence. Never forked or resumed from the implementer.

fork

Lead helper only

Replanning genuinely needs the conversation. (Fork disables child thinking — avoid for complex work.)
